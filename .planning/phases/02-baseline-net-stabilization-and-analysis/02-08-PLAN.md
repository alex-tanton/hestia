## Phase Goal

ROADMAP goal (verbatim): "The test suite passes deterministically on any weekday and household timezone, and a calibrated analyzer produces a triaged findings list, so removals can be attributed and trusted."

The goal is outcome-shaped but not written as a user story; it is not reframed here. Run `/gsd-mvp-phase 02` if a user-story framing is wanted.

<objective>
Land Phase 2's two branches the way CONTRIBUTING.md requires. Merge the finished clock branch into the knip branch (both are already on `origin` as backups, phase rule 4, so plain merges only), prove the clock branch against the current `origin/main` and the knip branch on top of it, and ask the owner once. Then push both final tips as fast-forwards, open the clock pull request into `main` (or mark 02-04's draft ready) and the knip pull request stacked on the clock branch, and get all six CI jobs green on each. After the owner squash-merges the clock pull request, confirm the knip pull request is open against `main` (recovering it if GitHub did not retarget it), merge `origin/main` into the knip branch, and prove its diff is exactly the four knip files with CI green before the owner squashes it.

Purpose: D-08 (knip committed via pull request) and the delivery of TIME-01 to TIME-05 to `main`. CI's `test-e2e` job is the E2E gate (the journeys need the full Docker Compose stack, which the cloud session does not guarantee), and CI's UTC runner is the zone where PR #1 went red.

Why stacked. `chore/knip-config` started from `origin/main` in plan 02-06, while the clock branch was still being built. On that base the seven time-dependent web test files fail (BASELINE.md), so the knip branch could pass neither `pnpm test` locally nor CI `test-unit` on a `main` base until the clock fix landed there. Both branches have been on `origin` as backups since their first plan (phase rule 4), so the knip branch is stacked by merging the clock branch into it, never by a rebase: every push stays a fast-forward and no force-push is needed. With the knip PR's base set to `test/deterministic-clock`, both PRs' required checks can pass on their own base, and the knip PR's diff shows only the knip change. The merge order is fixed: the clock PR first. When the owner squash-merges it and deletes its branch (CONTRIBUTING.md), GitHub normally retargets the knip PR to `main`. The PR's merge-base still sits below the separate clock commits, though, so its diff keeps listing every clock file. If GitHub does not retarget it, the PR may stay on the old base or be closed. Task 4 is therefore a `checkpoint:human-action` that pauses the plan until the owner's clock squash. Task 5 then confirms the knip PR is open against `main`, retargeting it or opening a replacement if needed. It then merges `origin/main` into the knip branch with a plain merge and checks that the diff is exactly the four knip files before the owner squashes it.

Context budget: if context runs short, stop after Task 3 and report. Task 4 is a pause point anyway, and a fresh executor resumes from `.planning/cleanup/logs/02-08-prs.txt`, which holds the decision, the PR numbers and the sync SHAs. In a new cloud session that file, the PR body files and the worktrees are gone (phase rule 12); Task 4 says how to restore them from GitHub before resuming. Tasks 1 to 3 restart in a new session from the branch backups on `origin` (phase rule 12).

Where the repo changes live: `files_modified` lists only the local log directory. Every repo change this plan makes (merge conflict resolutions, a regenerated `pnpm-lock.yaml`, CI fix commits, the Task 5 merge of `origin/main`, the GSD planning commit of `<output>`) happens inside the `../hearth-clock` and `../hearth-knip` worktrees and is carried by the branches `test/deterministic-clock` and `chore/knip-config`, never by the primary checkout.

Worktree names: `../hearth-clock` and `../hearth-knip` shorten CONTRIBUTING.md's `../hearth-{topic}` form (`../hearth-deterministic-clock`, `../hearth-knip-config`). The deviation is deliberate. Every Phase 2 plan creates and uses the short names, the directory names never leave the session, and the branch names follow `{type}/{topic}` exactly.

Output: the clock pull request green and squash-merged by the owner, and the knip pull request open against `main` with exactly the four knip files and green checks, ready for the owner's squash. The PR numbers, bases, SHAs and results are recorded. A merge into `main` triggers a push-to-`main` CI run and a Deploy run that waits for the unregistered self-hosted runner (CONTRIBUTING.md, "Deploys").
