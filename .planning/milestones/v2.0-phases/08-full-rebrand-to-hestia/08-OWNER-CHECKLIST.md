# Phase 8 owner checklist

Merging the rebrand into `main` runs CI and then Deploy on the self-hosted runner, which brings up a fresh `hestia` stack. These steps happen outside the repository, so no code can do them for you. The steps are numbered 1 to 17 and are meant to be done in order.

## Before merging

1. Create the new env file: `sudo install -d -m 700 -o "$USER" /srv/hestia`, then from a checkout of the branch run `scripts/generate-secrets.sh`. It writes `/srv/hestia/.env` with `HESTIA_*` names and new secrets, and refuses to overwrite an existing file. Set `HESTIA_ORIGIN` to exactly today's origin (the `HEARTH_ORIGIN` value in `/srv/hearth/.env`; the origin is pinned and must not change), and set `HESTIA_OWNER_EMAIL` and `BACKUP_DIR`. To keep the existing secrets instead (optional; the database is fresh either way): `sed 's/^HEARTH_/HESTIA_/' /srv/hearth/.env > /srv/hestia/.env` and `chmod 600 /srv/hestia/.env`. Check: `grep -c '^HEARTH_' /srv/hestia/.env` prints 0.
2. Runner label: in the repository, go to Settings, Actions, Runners, the self-hosted runner, and add the label `hestia`. Keep `hearth` until after the merge. The deploy job now asks for `[self-hosted, hestia]`; without the label it waits in the queue forever.
3. Every development machine: run `supabase stop --no-backup --project-id hearth` before pulling the merged `main` (the old local stack holds the ports and has the old login role), then `supabase start`. Rename any `HEARTH_*` shell exports to `HESTIA_*`.
4. Paste the PR body notes below into the pull request description.

## Merge and first deploy

5. Squash-merge. CI runs on `main`, then Deploy attempt 1 runs on the runner: `scripts/deploy-gate.sh` finds no `hestia-service:current` image and deploys.
6. Expected: attempt 1 builds both images, then stops with "the Supabase services are not healthy; nothing restarted", because the old `hearth` project still holds subnet `172.16.238.0/24` and `127.0.0.1:8080`. The old stack keeps serving. If the old stack was already down, attempt 1 succeeds; skip steps 7 and 8.
7. Stop the old stack and keep its volumes. First see what will stop: `cd / && docker compose -p hearth ps -a` lists the old project's containers by their project label (expect the old service, Caddy, database, auth, realtime, Kong and backup containers, and nothing from `hestia`). It uses the same no-Compose-file mode as the next command, which the planner checked with Docker Compose v5.6.1. Then run `cd / && docker compose -p hearth down` (no `-v`). Leave out `-f` on purpose, and run it from a directory with no Compose file. After the merge, the checkout's `docker/docker-compose.yml` describes the new `hestia` project, so `-f docker/docker-compose.yml` would need the new env file, target the new service and network names, and leave the old service container and the `hearth` network holding the subnet. With no Compose file, Compose finds the old project's containers and its network by their project label. Check: `docker ps -a -q --filter label=com.docker.compose.project=hearth` and `docker network ls -q --filter name=^hearth$` print nothing, and `docker volume ls -q --filter label=com.docker.compose.project=hearth` still lists `hearth_db-data` and `hearth_db-config`. Downtime starts here; a first deploy has nothing to roll back to.
8. Re-run the Deploy run (Actions, Deploy, Re-run all jobs): attempt 2 always deploys.
9. Check: `curl -fsS http://127.0.0.1:8080/api/health`. On the public origin, sign the owner up again (fresh database), create the household, re-invite members, and turn notifications on again on every device. On iPhone and iPad, remove and re-add the home-screen app to see the new name.

## After merge

10. Rename the repository: `gh repo rename hestia --repo alex-tanton/hearth` (assumption A1). GitHub redirects the old URL.
11. Every clone: `git remote set-url origin https://github.com/alex-tanton/hestia`.
12. Runner: reconfigure or re-register it against `alex-tanton/hestia` (its registration URL, service unit and `_work/` checkout path carry the old repository name), then remove the `hearth` label.
13. Cloud sessions: confirm the fine-grained PAT covers the renamed repository (`gh api repos/alex-tanton/hestia --jq .full_name`). `.planning/environment/cloud-check.sh` probes the new slug and fails until step 10 is done.
14. Dependabot: no configuration change (its paths are repository-relative). Confirm the next weekly run opens pull requests on the renamed repository.
15. In a follow-up pull request, delete `scripts/migration-exemptions.json` and its entry in `LEGACY_NAME_ALLOWLIST` (`scripts/check-repo-hygiene.mjs`); its entries are inert once the rebrand is on `main`. Do it before Phase 9 changes any migration.
16. Cleanup once the new stack is trusted: `docker image rm` the old `hearth-service:*` and `hearth-caddy:*` images; `docker volume rm hearth_db-data hearth_db-config` (the old database); optionally `docker builder prune --filter type=exec.cachemount` (drops the old `hearth-pnpm-store` cache mount); `sudo rm -rf /srv/hearth` (it holds the old secrets). Keep or prune old backups under the old `BACKUP_DIR` as you see fit.
17. Optional: if you rename the local checkout folder, also update the `file:///` link in `.planning/STATE.md`.

## PR body notes

- Environment names are a hard cutover: `HEARTH_*` became `HESTIA_*`, and a service started with the old names fails at startup. The host env file is now `/srv/hestia/.env`.
- Fresh deploy (D-04): the Compose project `hestia` creates new volumes; the old database is not carried over, so every user signs up again.
- Browser data (D-08): the persisted query-cache key and the notification-click message type were renamed. Each device starts with a cold cache once, and any offline writes queued on a device when it upgrades are dropped. A notification tapped while the page and the service worker are on different versions opens nothing special.
- The outbound User-Agent sent to Flipp and recipe sites changes from `Hearth/1.0 (...)` to `Hestia/1.0 (...)`.
- Installed PWAs are named Hestia; iOS may keep the old home-screen label until the app is re-added. The manifest description is unchanged.
- Owner CLI: `docker compose exec hestia-service hestia-admin reset-password <email>`; the old command no longer exists.
- Two applied migrations were edited in place to rename the login role to `hestia_service`; `scripts/migration-exemptions.json` pins exactly those two edits to their before and after blobs and is inert after merge.
- Developers: reset the local database after pulling (`supabase db reset`, or stop and start); the local login role and project id changed. The dev seed password is now `hestia-seed-pass-2026`, the reset password `hestia-reset-pass-2026` and the test database password default `hestia`, so a database set up with the old defaults needs its seed users reset or the `hestia_service` password changed.
- Merge only after steps 1-4 of `.planning/phases/08-full-rebrand-to-hestia/08-OWNER-CHECKLIST.md`.
