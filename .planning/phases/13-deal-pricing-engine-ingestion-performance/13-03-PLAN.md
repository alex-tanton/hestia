# Plan 13-03: PWA DealCard Pricing Display & Adaptive Ingestion Polling

## Context

In the PWA, deal cards currently display the discount badge in the secondary lower badge row, separating the discount percentage from the strikethrough original price. Furthermore, the deals client polling hook (`use-refresh-poll.ts`) relies on exponential backoff up to 60s that gives up after 10 attempts (~3 minutes), causing users to see premature timeout warnings before background ingestion finishes.

This plan refines `DealCard.tsx` to prominently anchor the primary unit price, place the discount badge inline next to the strikethrough original price, provide clean single-price fallbacks, and updates `use-refresh-poll.ts` and `DealFreshness.tsx` to poll every 4–5 seconds with a 3-minute hard ceiling per DEAL-01, DEAL-03, and locked decision D-08.

<threat_model>
### Security ASVS Level: 1 | Severity Threshold: HIGH

- **T-13-06 [Denial of Service - ASVS V5 Rate Limiting / Client Discipline]:** Polling storm from unthrottled or runaway client polling loops overloading the service during deal refreshes.
  - *Mitigation:* `useRefreshPoll` enforces a fixed 4.5s interval with a hard 3-minute ceiling (`MAX_POLL_MS = 180_000`, ~40 attempts), halting immediately when offline or once `refreshing: false`.
- **T-13-07 [Cross-Site Scripting / UI Injection - ASVS V5 Output Encoding]:** Injection of unescaped flyer strings or malformed pricing text into the browser DOM.
  - *Mitigation:* All price values and text strings are rendered using standard React JSX interpolation (automatic HTML entity encoding); currency formatting utilizes strictly typed integer-cents helpers.
- **T-13-SC [Supply Chain - ASVS V1 Architecture]:** Introduction of third-party polling or UI badge packages.
  - *Mitigation:* Implementation relies purely on existing `@tanstack/react-query`, standard React hooks (`useState`, `useEffect`), and Hestia design system components (`Badge`, `Card`).
</threat_model>

<action>
Update client deals polling in apps/web/src/screens/deals/use-refresh-poll.ts and freshness banner in apps/web/src/screens/deals/DealFreshness.tsx per D-08 and DEAL-03.

1. In apps/web/src/screens/deals/use-refresh-poll.ts:
   - Replace exponential backoff timing constants with fixed adaptive polling:
     - `export const POLL_INTERVAL_MS = 4_500;` (4.5 seconds fixed interval per D-08).
     - `export const MAX_POLL_MS = 180_000;` (3 minutes ceiling per D-08).
     - `export const MAX_ATTEMPTS = Math.floor(MAX_POLL_MS / POLL_INTERVAL_MS);` (~40 attempts).
   - Update `refreshDelayMs`:
     - `export function refreshDelayMs(): number { return POLL_INTERVAL_MS; }`.
   - In `useRefreshPoll(isRefreshing: boolean, refetch: () => void, isOnline = true)`:
     - Maintain state: `attempt`, `wasRefreshing`.
     - Reset `attempt` to `0` when `!isRefreshing`.
     - `isActive = isRefreshing && isOnline && attempt < MAX_ATTEMPTS`.
     - In `useEffect`:
       - If `!isActive`, return.
       - Schedule `setTimeout`:
         - `setAttempt((current) => current + 1);`
         - `refetch();`
         - Delay: `POLL_INTERVAL_MS`.
       - Cleanup with `clearTimeout(timer)`.
     - Return `{ isPolling: isActive, hasGivenUp: isRefreshing && attempt >= MAX_ATTEMPTS }`.

2. In apps/web/src/screens/deals/DealFreshness.tsx:
   - Verify that when `hasGivenUp` is true, the status line indicates that refresh is taking longer than expected (`" This is taking a while."`) and renders the `Try again` button affordance (`(stale || hasGivenUp) && <Button onClick={onRetry}>...`).

3. In apps/web/src/screens/deals/refresh-poll.test.ts:
   - Update unit tests:
     - Verify `refreshDelayMs()` returns `POLL_INTERVAL_MS` (4,500ms).
     - Verify `refetch` is called repeatedly at 4.5s intervals while `isRefreshing` is true.
     - Verify polling immediately halts when `isRefreshing` resolves to false.
     - Verify polling stops after `MAX_ATTEMPTS` (40 attempts / 180s) and marks `hasGivenUp: true`.
     - Verify no polling occurs while `isOnline: false`.
