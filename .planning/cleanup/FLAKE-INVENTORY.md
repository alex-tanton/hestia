## Classification rules

Failures in CI and Sweep history are classified using these ordered rules:

1. **`intentional`**: The ledger records the run as deliberate red regression or canary evidence (for example canary run 40023558441 in `CI-ENFORCEMENT-LEDGER.md`, FIX-07 run 39457296052 and FIX-02 run 39440151507 in `FIX-LEDGER*.md`).
2. **`infra`**: An infrastructure failure signature occurring within its expected step: setup steps (pnpm, node, or Supabase setup), image pre-pull steps (`ci-prepull-images` or `docker pull`), the `supabase start` step, or `pnpm test:e2e` when no Playwright test results were produced (stack never came up). The same string anywhere else, for example in a test output, does not make the attempt infra.
3. **`real`**: Every attempt and run on that head SHA fails in the same way, explained by a code, dependency, or configuration state on that head (cited with the commit or PR that resolved it).
4. **`flaky`**: Either (a) a later attempt of the same run, or another run on the same head SHA, passed that job, or (b) the same test (spec file and title) is flaky by (a) on another head and the diff between the two heads does not touch its spec file.
5. **`unexplained`**: Any failure not matching the above, treated as a candidate for root-cause diagnosis in plan 06-14.

## Root causes

### F-01: tests/19-notifications.spec.ts:140 notifications — meal reminder with the push double (light) › enables a type, delivers its reminder once, and a tap opens its household
- Symptom: `expect(switcher(page)).toHaveText(/Oak Street/)` times out after 15,000ms with `Received string: "Rivera Family, switch household"`.
- Evidence: Preserved traces from all 7 failed CI runs (`.planning/cleanup/logs/06-14-traces/`) show `GET /api/users/me` and `PUT /api/users/me/active-household` dispatched at the exact same millisecond ($\le 4\text{ms}$ difference) upon landing on `/meals?household=...`. Local reproduction log `.planning/cleanup/logs/06-14-repro-F-01.log` (2 failures in 5 iterations) and trace analysis notes `.planning/cleanup/logs/06-14-notes-F-01.md`.
- Mechanism: In `apps/web/src/screens/AuthenticatedLayout.tsx`, `useProfile()` mounts with `staleTime: 0`, immediately firing `GET /api/users/me`. Concurrently, `useNotificationTarget` (`apps/web/src/lib/push/notification-target.ts`) reads `?household=...` from URL search params and calls `useSwitchHousehold().mutate(householdId)` (`PUT /api/users/me/active-household`). On the backend, `GET` queries `profile` before or concurrently with `PUT` committing, returning `Rivera Family`. In `apps/web/src/lib/api/hooks.ts`, `useSwitchHousehold` updates `queryKeys.profile` on `onSuccess`, but does not cancel in-flight profile queries via `onMutate`. When the stale `GET /api/users/me` response resolves in the browser, React Query updates `queryKeys.profile` with `Rivera Family`, overwriting the optimistic/mutated household. Because `useNotificationTarget` deletes `?household=` and marks the location as handled, it never switches again.
- Class: product
- Repro: `HEARTH_E2E_REUSE_STACK=1 HEARTH_E2E_RUN_ID=repro01 pnpm --filter @hearth/e2e test:e2e tests/19-notifications.spec.ts:140` against isolated local Compose stack `repro01` in throwaway worktree `/home/user/hearth-flake-repro-2`, with a 25ms response delay on `GET /api/users/me` via Playwright route interception. Measured 2 failures in 5 iterations (40% failure rate) logged in `.planning/cleanup/logs/06-14-repro-F-01.log`.
- Fix: In `apps/web/src/lib/api/hooks.ts` in `useSwitchHousehold`, add `onMutate: async () => { await queryClient.cancelQueries({ queryKey: queryKeys.profile }); }` to abort/cancel any in-flight profile queries before the active household mutation completes.
- Regression test: `apps/web/src/App.test.tsx` (Vitest unit/integration test) simulating concurrent profile revalidation and active household mutation; plus `e2e/tests/19-notifications.spec.ts:140` under local repro conditions.
- Confidence: high
