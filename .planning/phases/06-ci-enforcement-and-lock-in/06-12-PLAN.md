## Phase Goal

ROADMAP goal (verbatim): "CI blocks regressions of everything this milestone cleaned, without turning `main` red or breaking the `CI`-triggers-deploy contract"

Gap being closed (06-UAT.md, G-06-3, severity major): "The deploy gate does not redeploy a commit that is already running". The owner (2026-10-24): "The deploy gate should not redeploy the same commit, but I still don't understand why that would happen."

Why it happened, for the owner and for the pull request body: Deploy runs every time a `CI` push run on `main` completes green (`workflow_run`, `types: [completed]`), and a run completes once per attempt, so re-running any job of a run (for example to look at a flaky test) completes it again and starts another Deploy run for the same commit. History shows this: `CI` run 39718363858 on `a5c4384` had three attempts and produced three Deploy runs (39719463322, 39720541360, 39721751275). Re-running a Deploy run does the same. When that commit is already the running one, `scripts/deploy-gate.sh` deliberately answered `deploy=true` (PC-5 kept the old "a re-run always redeploys" behavior), so production was rebuilt and restarted with nothing new. After this change it answers `deploy=false`, and a deliberate redeploy keeps an explicit path, because a deploy that failed after `scripts/deploy.sh` had already tagged the new images `current` (its `switch_to` tags before `compose up`; a first deploy has no rollback target) leaves the running label equal to the commit that still needs deploying.

What it restores: CI-05 (the workflow correctness review, whose OD-4 rules this gate implements) and CI-07 (`CI` triggers deploy correctly). It is a deploy-behavior change (D-20): the pull request body flags it before the merge (06-13). 06-16 adds the requirement notes; nothing in ROADMAP.md or REQUIREMENTS.md changes here.

The owner's answer on the deliberate redeploy (2026-10-24, recorded as OD-7 `rerun-deploy` in Task 2): "A deliberate redeploy should work by Re-run the Deploy run (planner's recommendation). A re-run of the Deploy run itself is allowed to redeploy the running commit. A re-run of CI is not." The two cases are told apart by the Deploy run's own attempt number: a `CI` re-run starts a new Deploy run, whose `github.run_attempt` is 1, while "Re-run" on a Deploy run raises that run's `github.run_attempt` to 2 or more.

Which parts need the owner's hand-off: only `.github/workflows/deploy.yml` (its comments, plus one `env` line passing `github.run_attempt` to the gate as `HEARTH_DEPLOY_ATTEMPT`; no new trigger). The token has no `workflow` scope, so that one commit reaches `origin` through 06-13's patch and `apply.sh`. Everything in this plan (`scripts/`, docs, `CONTRIBUTING.md`, `README.md`, `.claude/CLAUDE.md`) goes through a normal push and the same pull request.

MVP mode asks for a user story. The goal is outcome-shaped but not written as a user story, so it is not reframed here (no story is invented).

<objective>
Make the deploy gate skip the commit that is already running (test first, then the fix), build the owner's deliberate-redeploy path (a re-run of the Deploy run itself redeploys, a re-run of `CI` does not; test first, then the fix), bring every document that describes the rule up to date, run the local gates and push the branch without its workflow commit.

Purpose: a re-run of `CI` or of Deploy should never rebuild and restart production for a commit it is already running, and the owner asked to understand why it did; a deploy that failed half-way must still be retryable on purpose.

Output: `fix/deploy-gate-running-commit` on `origin` (W5), OD-6 and OD-7 in the ledger, red and green evidence, the gate logs.
</objective>
